Which build route runs?

All four intake types use the same controller. Your chosen output class determines the native build sequence. The default worker always handles routing.

Code code
  1. Build Auto
  2. Verify code
  3. Code files
Document non-code
  1. Product Brief
  2. Verify brief
  3. Product brief
Both mixed
  1. Build Auto
  2. Product Brief
  3. Verify both together
  4. Code + brief
Default-worker build
Any output class
  1. Codex adapter or trusted executable builds from the route
  2. Verify snapshot
  3. Requested text files

Native execution accepts Build Auto and Product Brief. Other document workflows, deployment, binary outputs, and worktree integration are separate work. For a run-local operator guide or research synthesis, arrange a default-worker build that can produce it. Native document delivery includes a Product Brief.

What the controller hands to each worker

Each attempts/<n>/job.json carries the original request and checks, owner answers, current route, previous artifacts and check feedback when present, and remaining calls and timeout. A workspace agent uses status to locate native jobs, runs native_host.py prepare, serves the named workflow in the isolated attempt workspace, then uses submit with terminal evidence and artifact paths. --native-worker serves those same jobs through a trusted executable. Native language settings default to English and can be set separately for communication and document output.

Workers write durable receipt.json files. A mixed run stages the code receipt before dispatching the brief, so the document job sees the saved code. The controller checks native evidence hashes and checks that v2 artifacts match their source evidence.

When does it ask you?

Authority controls when a route can start or replace the currently selected deliverable. A worker can also ask an owner question in any phase.

A · Approve a proposal

Propose → owner approves → build

The first proposal and every replacement wait for your explicit approval.

B · Delegate within limits

Check boundaries → proceed or pause

An in-scope proposal or replacement can proceed. A mismatched name under prose limits with no name allowlist requires approval. A structured-boundary violation stops before that route can build.

C · Name the deliverable

Exact match → build

A different initial name or any replacement requires your approval.

Mode B can constrain the output class, exact deliverable names, or both. Prose limits guide workers through every phase. The controller checks the structured fields and the route name. Keep the same run when answering or approving.

What belongs in the request

Set intake.kind to idea, literature, brainstorm, or forge and include the source text. Record kind, authority.mode, authority.outcome, owner limits and any exact deliverable label, and at least one check with a stable ID. Set a positive budget and optionally timeout_seconds, which defaults to 600 per call.

How it proves delivery

Every original check must pass. Typed checks bind the result to the artifact snapshot’s SHA-256 hashes. The controller checks those hashes again before publishing.

  1. Staged filesHash the snapshot
  2. Run original checksDefault worker or independent checker
  3. Resolve the verdictPass all → publish. Fail or inapplicable → repair. Checker fault → reverify.
  4. Publish and recordVerified files in artifacts/ plus status and hashes

Executable

Trusted --verify-worker runs the files and records the command, exit status, and output.

Source inspection

Exact lines and quotes from the artifact, original intake, or both, as required by the check.

Judgment

Verifier explains its criteria and assessment. The verdict is labeled as judgment.

Each new route, build, verify, and retry dispatch consumes one call. Publishing uses the saved results. Native workflow subcalls have their own host budgets. status reports dispatch and usage coverage. Share telemetry.json for diagnosis and keep the original run records private.

Storage and size limits

A run holds state.json, attempt jobs, worker logs and receipts, then verified files under artifacts/. New runs write a local telemetry.json with fixed diagnostic labels, counts, and timings. telemetry RUN also exports it from saved state. The request file is capped at 512 KiB. Each serialized receipt is capped at 4 MiB. The Codex adapter reads jobs up to 8 MiB, including the joint snapshot for mixed verification. Use run-local UTF-8 text files within those limits.

Where you choose the model

Pick the worker for each stage first. Then set the model in the place that runs that worker.

WorkerStagesCustomization
--codexRouting, default-worker builds, default verification--model MODEL and --effort low|medium|high|xhigh. One override pair applies to every stage this worker handles. Omit either flag to use the configured Codex setting. Use a model ID and effort your provider and account support.
--native-hostNative buildsChoose the model and reasoning settings in the workspace agent host. Nested workflow calls use that host’s tooling and budget. Build Auto’s workflow.implementation_handoff can choose a separate model or tool for delegated implementation when the host supports it.
--native-worker PATHNative buildsThe executable integration chooses its provider and model. It can dispatch differently for Build Auto and Product Brief while preserving the fixed sequence and receipts.
--worker PATHRouting, default-worker builds, default verificationThe trusted executable can choose a model per job.phase or handle a phase locally. Its own configuration supplies model and provider choices.
--verify-worker PATHVerification onlyUse a local checker for typed executable behaviors. Its configuration controls any downstream model use. A deterministic browser or runtime checker can run locally.

Model and effort flags apply only to the Codex adapter, even in a native run. They are start-time settings. For separate settings per phase, use a custom worker or combine the default worker with a separate native host or verifier.

Show a Codex model override example 
python3 "$DELIVER" start "$RUN" --request request.json \
  --codex --model "$MODEL" --effort medium --native-host \
  --verify-worker /path/to/checker

In this example the adapter uses MODEL for routing. The workspace host serves the build. The separate checker owns verification. MODEL is an ID configured for your provider. When the Codex adapter handles a stage, it opens a fresh read-only session and sends the job to that provider. Use authorized material for the selected worker.
