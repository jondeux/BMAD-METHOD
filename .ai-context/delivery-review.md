# Autonomous delivery beta review and approval plan

Extract `delivery-review-evidence.zip` beside this file to open the local evidence links. Reviewed revision: `891b0063`.

**BMAD Autonomous Delivery meets its narrow beta milestone. Its biggest gap is that the controller can declare success without establishing two things the user cares about most: that the agent stayed within its delegated authority and that the delivered artifact actually passed its checks.** I confirmed both gaps with local checks against the pushed handoff. The beta also has evidence worth preserving: a mixed run recovered a completed build after interruption, a fresh installation produced a source-faithful brief, and all 12 delivery tests passed again during this audit. I recommend fixing authority, verification, and recovery before expanding native workflow coverage. [Milestone specification](review-evidence/specs/spec-bmad-native-delivery/SPEC.md) · [Beta verification report](../.ai-context/delivery-beta/REPORT.md)

## The project and the bar

I reviewed **`bmad-deliver` at handoff commit `891b0063`**, alongside the earlier breadth pilot and subsequent live-run evidence. Its user is a project owner who brings an idea, literature, brainstorming output, or Forge result and wants usable code, documents, or both. The owner chooses how much authority to delegate through A, B, or C. Excellence means the owner can leave during ordinary work, return to the same run, and tell what was delivered, what proves it, what it cost, and which decisions still belong to them. The constraints are local outputs, authorized tools and providers, low spend, and explicit owner control over consequential changes. [Project handoff](../.ai-context/handoff.md#L12-L25)

**My inference about the dissatisfaction:** the pilot answers “Can BMAD's parts handle a wide range of situations?” The owner’s everyday question is “Can I leave this particular job with it?” The evidence for the first is broad. The evidence for the second is narrower, especially for ambiguous delegation, failed checks, and document types beyond a brief. The fork’s GitHub issue search returned no issues. I therefore treated the recorded checker failure, model rejection, sandbox denial, and renderer mismatch as **observed operator incidents**. Real-customer satisfaction and incident frequency remain unknown. [Pilot results](review-evidence/forge-autonomous-bmad-delivery/pilot-2026-11-24/REPORT.md) · [Live incident report](review-evidence/forge-autonomous-bmad-delivery/live-2026-11-25/run-evidence-tlPetZ/REPORT.md)

Three external benchmarks informed the review. Temporal makes execution history and retry behavior inspectable. LangGraph exposes durable checkpoints and explicit human interrupts. Anthropic’s agent-evaluation guidance measures the outcome in the environment and distinguishes that outcome from what the agent says happened. BMAD’s opportunity is to combine those practices with something specific to this project: **owner-selected authority, BMAD workflow evidence, and acceptance of the actual deliverable**. That can be done incrementally with the current Python controller. [Temporal event history](https://docs.temporal.io/encyclopedia/event-history) · [LangGraph interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts) · [Anthropic’s agent evaluation guidance](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

### What is easiest to miss

- **A valid receipt answers a narrower question than an owner asks.** A checksum establishes which bytes were recorded. A check ID establishes which requirement the verifier addressed. Neither establishes that a command executed successfully or that a document claim follows from its source. The 74-word library example is instructive: it preserves the decision owner and study limitation, while its two open questions leave trial scope and success criteria for Library Operations. Whether that is sufficient depends on the decision the owner asked to make. [Sample brief](../.ai-context/delivery-beta/library-trial-brief.md) · [Editorial assessment](../.ai-context/delivery-beta/native-editorial-review.md)
- **The weakest assumption is that a capable worker will interpret delegated limits exactly as the owner does.** Mode B is the feature that most reduces interruptions. It is also where the controller most readily adopts a worker’s judgment. Requiring approval for every B choice would defeat the feature. Recording the allowed choices once and escalating only an unresolved boundary preserves its value. [Authority design](review-evidence/forge-autonomous-bmad-delivery/pilot-2026-11-24/REPORT.md)
- **At scale, apparently cheap recoveries can become expensive.** A failed independent verification sends the run back to build. The special `--reverify` path requires an exhausted budget and a failed independent check. The team already encountered a real checker defect for which rebuilding correct SQL would have been wasted work. [Verification transition](../skills/method/bmad-deliver/scripts/deliver.py) · [Observed checker repair](review-evidence/forge-autonomous-bmad-delivery/live-2026-11-25/run-evidence-tlPetZ/REPORT.md)
- **The useful comparison is direct use of the native skill.** An owner who already knows they need one Product Brief has a simpler starting point. Autonomous Delivery earns its additional orchestration when it demonstrates fewer owner interruptions, safer recovery, or better acceptance across a handoff. The pilot established examples of all three behaviors, but it did not measure that incremental value against direct skill use. [Beta evidence](../.ai-context/delivery-beta/REPORT.md)

### Sequence, stopping points, and cost

1. **Start with U1, U2, and U3.** U2 and U3 can proceed in parallel if their shared run-record changes are coordinated. This is the first stopping point: users can understand the beta’s scope, and new runs gain enforceable delegation and stronger acceptance.
2. **Then U4.** U5 and U6 can proceed alongside it once the attempt and receipt fields are settled. This is the second stopping point: the beta becomes easier to operate, diagnose, and update.
3. **Run U7 before choosing expansion breadth.** Its scorecard and case design can start earlier. **U8 depends on U2, U3, U6, and U7.** Existing route parity is a release condition.
4. **Delivery estimate:** eight revertible Conventional Commits across roughly five to seven working sessions. Those are planning estimates. Each upgrade gets its own proof and deviation report. Commit and push require your separate instruction.

**Planned live-model spend is $0. Largest paid run: none.** The plan covers implementation, deterministic tests, historical replay, and owner assessment of existing artifacts. A fresh live benchmark or promotion of the experimental Ingest route would require a separate proposal. The smallest useful promotion run is one source packet through Ingest and delivery with the requested `gpt-6.2-sol` medium orchestrator, adding `gpt-6.1-terra` high only if testing a simulated stakeholder is necessary. The recorded harness rejected a requested model on this account, and I found no verified billing rate for this exact setup. A dollar estimate would be speculative until model availability, token ceilings, and billing are known. [Recorded harness result](review-evidence/forge-autonomous-bmad-delivery/pilot-2026-11-24/extensions/REPORT.md)

**Rule check:** the upgrades fit the repository’s `AGENTS.md`, including deterministic testing, Conventional Commits, explicit push authorization, and the release restriction on `main`. U5 concerns private **content** and diagnostics, and U8 concerns raw-source retention. Approving either authorizes only the data-handling changes described above. No dependency upgrade, Python version change, Space SDK change, public `run_research()` change, key-management change, Claude-plan rule change, or spending is required. I found no delivery web UI, Space, or `run_research()` surface in the audited implementation. The affected interfaces are the CLI, repo-scoped skill, workspace host, and beta archive. ### Stop doing

- Stop presenting route predictions, native executions, and owner-accepted deliverables under one coverage number. Each is valuable and answers a different question.
- Stop treating a dispatch cap as an estimate of money spent. Some historical token usage can already be recovered for free.
- Stop rerunning known repaired examples as the main evidence of improvement. Keep them as regressions and reserve fresh cases for assessing generalization.
- Stop expanding the adapter catalog until each new entry can explain what it produces, how it finishes, how it recovers, and what evidence makes it eligible for use.

**Open owner question:** for U7, which real deliverable would you most want to receive without intervening: a decision-ready document, a working code change, or a mixed package? A redacted example and your definition of “usable on first delivery” would let us test the source of dissatisfaction directly. This can wait until U7.

**Audit verification:** both CLI help commands ran, all 12 targeted delivery tests passed, the archive checksum and 41 member hashes matched, and the handoff worktree was clean afterward. The beta report’s 1,259-test full-suite result is historical. I made no project edits, installed no packages, changed no settings, and started no paid model run.
