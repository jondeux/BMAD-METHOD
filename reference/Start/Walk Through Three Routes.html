Walk Through Three Routes

This walkthrough builds three new projects of different sizes. Together they show BMad’s core idea: it sizes the planning to the work.

PartThe workRouteTime
1. Quick buildA meeting cost timer, one sessionStraight to bmad-buildAbout 15 minutes
2. Product Owner routeA small web app, a few storiesSofia, the Product Owner, then buildAbout 45 minutes
3. Full routeA company tool, several epicsBrief, PRD, UX, epics, architecture, stories, one epic built, retrospectiveAbout 2 hours

Jump to the part that matches your work, or do all three in order.

Before You Start

Each part is a new project. Give each its own Git repository with at least one commit, then install BMad and run bmad setup in it. In one shared repository, a later part would build on the code an earlier part left. Parts 2 and 3 build Python apps, so have Python 3 installed too.

Terms You’ll See

Section titled “Terms You’ll See”
TermMeaning
InitiativeThe folder that holds all the planning for one app.
EpicOne large part of an app, made of stories.
StoryOne small piece of work you can build in a single session.
BuiltThe code for a story is written, tested, and committed, ready for you to check.
DoneYou checked a built story and told Sofia, who marks it done.
Step-by-step, freeform or fastStep-by-step and freeform go through each section with you; fast drafts everything for you to correct. This walkthrough always picks fast.

How the Steps Work

Section titled “How the Steps Work”

Most steps follow the same pattern:

  1. Ask /bmad What's next?
  2. BMad suggests the next skill. Say “Yes,” unless the step gives you a different reply. If it asks whether to start the skill here or in a fresh session, say “Start it here.”
  3. The skill asks for something. If the step has a text block, paste it.
  4. Answer its other questions, using the notes in the step.

The first step of each part uses its own prompt instead of What's next?. Start each part in a new session. Within a part, each step says whether to stay in the session you’re in or start a new one. BMad works out what’s next from the files you’ve already made.

The agents word their questions differently every time, so this is not a script. Answer what they ask. The notes cover the questions that change the outcome; for any other question, take the option the agent recommends.

Your coding tool asks before an agent runs a command it hasn’t run before, such as the tests or a browser check. Allow those, or the checks are skipped.

Part 1: Quick Build

Section titled “Part 1: Quick Build”

Work that fits in one session but isn’t trivial goes straight to bmad-build. It plans the work, writes it, checks it, and commits it, with no planning documents and no initiative.

The work is a web page that shows how much a meeting is costing, live. Everyone has sat in a meeting that should have been an email. Ask:

If it shows a plan, say “Approved.” A change of about 100 lines or fewer goes straight to the code without one. You end up with a working meeting cost timer that opens in your browser.

Part 2: Product Owner Route

Section titled “Part 2: Product Owner Route”

A web app with a few features is too big for one session, but one clear idea doesn’t need a PRD, UX design, or architecture. Sofia, the Product Owner (bmad-agent-po), writes the requirements straight from your idea and splits them into stories. Then you build them one at a time.

1. Write the Requirements and Stories

Section titled “1. Write the Requirements and Stories”

Create the initiative:

In the same session, ask /bmad What's next?. BMad suggests Sofia; say “Yes.” She turns your idea into a numbered list of requirements, then splits the work into stories. When she asks what you want to build, or starts asking her own questions about it, paste:

Then answer her:

  • When she lists the guesses she made, say “All fine.”
  • When she asks how to split the work, say “Straight into stories, no epics. Three or four small ones. Make the first one a thin slice that works end to end.” Without this, she would split the work into epics.
  • When she shows the stories and asks to save them, say “Yes.”

The initiative now holds numbered requirements and the stories in the order to build them.

2. Build Story 1

Section titled “2. Build Story 1”

In a new session, ask /bmad What's next?. BMad suggests bmad-build for story 1; say “Yes.” Then:

  • If it says there are uncommitted changes, such as the BMad setup files, say “Commit them first.”
  • If it shows its plan, say “Approved.”

You get working code, tested and committed, and story 1 is marked built. To see it, ask “How do I run the app?” It gives you the command that starts it and the address to open in your browser. Start it, book a free slot, and reload the page to check the booking is still there.

3. Mark Story 1 Done

Section titled “3. Mark Story 1 Done”

In a new session, ask /bmad What's next?. BMad suggests marking story 1 done with Sofia once you’ve checked it in your browser. It may also offer a code review, which has more agents check the code; marking it done tells Sofia it works. Say “I checked it in my browser. Mark it done with Sofia.”

Story 1 is done, and story 2 is next. Keep asking /bmad What's next? for story 2 onward.

Part 3: Full Route

Section titled “Part 3: Full Route”

Now the same idea as a real company tool, close to the room booker the rest of these docs use. More people, more screens, and two roles, staff and office managers, mean more can go wrong, so each planning step catches something the others would miss. Then you build one epic and judge it.

Here UX runs before Sofia writes the initiative, so its files feed her requirements. Plan a Feature as a Team shows the other order, where Sofia writes and slices first.

1. Start a New Initiative

Section titled “1. Start a New Initiative”

The new initiative becomes the active one, so BMad works on it by default. Part 2’s initiative stays as it was. BMad may go straight on to the brief.

Outside This Walkthrough

You don’t need to list the documents. Tell John, the Product Manager, what you’re trying to achieve, and he proposes the planning document that fits and says why. Part 3 names the brief and the PRD so every reader gets the same run.

2. Write the Brief

Section titled “2. Write the Brief”

A brief is a one- or two-page summary of the product, why it matters, and who it’s for. Mary, the Business Analyst (bmad-agent-analyst), writes it. If she hasn’t started already, ask /bmad What's next? in the same session; BMad suggests her; say “Yes.” When she asks you to describe the product, paste:

  • Answer her questions as best you can, inventing sensible details if you need to. If she asks about linking to the company calendar, say “No, standalone.”
  • When she walks through her guesses or her reviewers’ findings, take her suggestions. If she shows a table of wording edits, say “Apply them all.”
  • When she shows the draft, say “Make it final.”

3. Write the PRD

Section titled “3. Write the PRD”

A PRD (product requirements document) says in detail what the product must do. In the same session, ask /bmad What's next?. BMad suggests John, the Product Manager (bmad-agent-pm); say “Yes.” He may ask a few questions first. Paste this, with the details below it:

The details:

  • Offices: London, Manchester, and Leeds, with 10 to 15 rooms each.
  • A booking has a room, time, length (15 minutes to 4 hours), title, and attendees.
  • Overlaps are never allowed.
  • Anyone can see a booking’s room, time, title, and who booked it.
  • Check-in, visitors, catering, desk booking, and links to outside calendars are not included.

If he points out that 300 staff can’t reach an app on your computer, say “My computer is for building and testing. Leave hosting to the architecture.” If he points out that anyone can pick anyone’s name, say “That’s fine for the first release. Sign-in comes later.” When he shows the draft or starts walking through his guesses, say “Make it final.” He records the guesses you skip as open assumptions.

4. Design the UX

Section titled “4. Design the UX”

UX design covers how the app looks and how people use it. In the same session, ask /bmad What's next?. BMad suggests bmad-ux, the UX skill that Sally, the UX Designer, runs; say “Yes.” It works from your brief and PRD. When it asks how the app should look and work, paste:

  • If it asks about the front end, say “No preference, keep it simple.”
  • When it walks through its decisions, take its suggestions.
  • When it offers a review and mock-ups, say “No.”

You get DESIGN.md for how the app looks and EXPERIENCE.md for how it works.

5. Write the Requirements and Split Them into Epics

Section titled “5. Write the Requirements and Split Them into Epics”

In a new session, ask /bmad What's next?. BMad suggests Sofia; say “Yes.” She turns the brief, PRD, and UX into numbered requirements in the initiative, then splits the work into epics.

  • When she lists the guesses she made, say “All fine.”
  • If she asks where the list of people comes from, say “A seed file for now.” For anything else she asks you to decide first, take her recommendation.
  • When she asks whether to split the work into epics now, say “Yes. Make the first epic offices and rooms, because nothing can be booked until the rooms exist. Put deployment in a later epic of its own.” Without the last sentence, epic 1 can only close once the app is deployed.
  • When she proposes the epics, such as offices and rooms, booking, and the calendar, say “Looks good, save it.” She commits the plan.
  • If she offers to start the architecture, say “Not now.” You’ll do that in a new session.

6. Settle the Architecture

Section titled “6. Settle the Architecture”

Architecture is the set of technical rules every epic follows, so parts built separately fit together. In a new session, ask /bmad What's next?. BMad suggests bmad-architecture, which Winston, the Architect, runs. Your epics all share the people and rooms, the booking rules, and the calendar, so they need agreed rules before anything is built. Say “Yes.” When it asks whether to coach and what you need besides the document, paste:

Keep “skip the reviewer gate”

Without it, three reviewer agents check the draft, which can take more than 20 minutes. On a real project you would let them run. If reviewers start anyway, say “Stop. Skip the reviewer gate.”

  • When it shows the draft and asks you to confirm its guesses, such as who can reach the app or the front-end library, say “Fine.”
  • If it offers slides or diagrams, say “No.”
  • When it offers to hand the document to Sofia, say “Yes.” If she flags anything in your plan that conflicts with the architecture, say “Side with the architecture.” If she goes on to refine the first epic, say “Commit it. I’ll refine the epic in a new session.”

The architecture document is now linked to your epics.

7. Plan the First Epic’s Stories

Section titled “7. Plan the First Epic’s Stories”

In a new session, ask /bmad What's next?. BMad suggests Sofia, to refine the first epic and plan its stories; say “Yes.”

  • When she lists the epic’s open questions, each with the answer she recommends, say “Go with your picks.”
  • When she proposes the stories, say “Two stories only, to keep the walkthrough short. Both run on my computer, with no deployment yet.” Without the last sentence, she may put a production deployment in story 2, which you can’t build here.
  • When she shows the stories and asks to save them, say “Yes.”

Do this once per story. In a new session, ask /bmad What's next?. BMad suggests bmad-build for the next story; say “Yes.” Then:

  • If it says there are uncommitted changes, such as the BMad setup files or the team file from the tip, say “Commit them first.”
  • If it shows its plan, say “Approved.”

To see the app, ask “How do I run the app?” Run the commands it gives you and walk the checks the build lists, in your browser at laptop width and at phone width (your browser’s device mode). Sofia relies on this check when she checks Done when at the close. Then, in a new session, ask /bmad What's next?. BMad suggests checking the story by hand, sometimes a code review, and marking it done with Sofia; say “I checked it at laptop and phone width. Mark it done with Sofia.” Repeat the step for story 2.

9. Run the Retrospective, Then Close the Epic

Section titled “9. Run the Retrospective, Then Close the Epic”

Once both stories are done, run the retrospective, which judges the finished epic as a whole against what it was meant to deliver. In a new session:

It may first ask what to look at harder; say “None.” It shows its findings, action items, and a verdict, then offers decision records and a team discussion. Say “Accept the verdict. No decision records.” A plain “Accept” can also write the decision records it offered. The retrospective is saved in the epic’s folder.

Then, in a new session, have Sofia validate the epic against its Requirements and Done when, and close it, as in Finish an Epic:

She checks each item of Done when first. If she says the epic needs the deployed app, say “Close it for running on my computer and move deployment to a new epic.” If an item hasn’t been checked, such as the phone width, check it now and tell her what you saw. Then confirm. Keep asking /bmad What's next? for the next epic.

What You Built

Section titled “What You Built”

A one-page app built in a single session, a hobby app built story by story from Sofia’s requirements, and the first epic of a company tool, planned from a brief through architecture, built, judged, and closed. The planning grew with the work: none for the timer, Sofia’s requirements for the hobby app, and every planning document for the company tool.

Walk Through an Existing Codebase picks up the company tool once it is finished, as code you inherit.

Key Takeaways

Ask /bmad What's next? whenever you are unsure; BMad reads the files you have made and suggests the next step. Start each step that says so in a new session, so the agent works from the files and not from an old conversation.
