tea-evaluate CLI

tea-evaluate CLI

Section titled “tea-evaluate CLI”

tea-evaluate is the runtime behind the Evaluate skill (bmad-tea-evaluate). It validates an evaluation folder, qualifies each seeded probe in a disposable workspace, runs every arm a probe needs as sealed trial sets, scores them through eval-quality score, compares the result with a committed baseline and runs the checks of one CI tier from the evaluation’s own plan. Eight subcommands cover those jobs. A ninth, opt-in experiment command analyzes supported saved Test Design records or prepares a bounded proposal. TEA also ships tea-skill-runner, the command an evaluation registers to run a skill.

CommandWhat it doesExit codes
checkValidates the folder and lists every authoring defect0, 10, 12, 64
digestWrites corpus-index.json and prints a digest0, 10, 12, 64
preflightQualifies each seeded probe and drives the preflight legs against the real target0, 3, 4, 5, 10, 11, 12, 64
runRuns the preflight, then every arm a probe needs, and seals the trials0, 3, 4, 5, 10, 11, 12, 64
statusReads a run’s current progress; --follow reports updates until it ends0, 12, 64
scoreScores the trial sets of a completed run0, 2, 3, 4, 5, 10, 12, 64
compareSets a scored run beside baseline/, and with --accept replaces the baseline0, 10, 12, 64
ciRuns the checks the CI plan places on one tier0, 1, 2, 3, 4, 5, 10, 11, 12, 13, 64

Exit 0 does not always mean the target passed: Exit codes says what each exit means for each command.

How Evaluate Works explains why these pieces exist, and Why Evaluate Confines the Target explains the confinement. Four companion reference pages hold the detail behind the commands, and a link to a section that moved to one of them lands on its entry here:

  • tea-evaluate Manifest: the evaluation.json fields, held-out probes and partition plans, operation phases, the registry, the HTTP port, the launch, the workspace, the interaction plan, controlled mutations, historical probes and gameability probes.
  • tea-evaluate Confinement: what a confined target can read, write and reach on macOS and Linux, the audit, egress and subscription logins.
  • tea-evaluate Evaluators: the evaluation layer, the rubric judge, judge calibration labels and sealed-brief agent qualification.
  • tea-evaluate Evidence: the run directory, the path forms in the records and the run-wide strength aggregate.

Experiment

Section titled “Experiment”

tea-evaluate experiment --saved <directory> --out <new-directory> reads saved Test Design evidence. Use --search-root <directory> for latest-record discovery, --propose <agent-prepared-declaration.json> for a proposal, or --recover <experiment-directory> for unresolved reservation reports. No --evaluation is required for this separate opt-in route. It preserves the eight existing command paths and makes no model call during saved analysis. Native live execution is blocked by telemetry and enforceable-budget gaps. See supported records and limits.

Prerequisites

Section titled “Prerequisites”
  • Node.js 22.20 or later, with TEA installed in the evaluations folder (the evaluations_folder setting in _bmad/custom/bmad-tea-evaluate.toml, evals by default and in these examples) through its private package.json (npm install --prefix evals), which provides the tea-evaluate and tea-skill-runner bins. The adopter’s root manifest stays untouched, so every invocation names the folder: npm exec --prefix evals -- tea-evaluate ... and npm exec --prefix evals -- tea-skill-runner ..., run from the project root.
  • eval-quality 10.1.1 or later, a devDependency of the same private package.json. TEA declares it as an optional peer dependency, so a project that installs TEA only for its other skills never receives it. Without it, tea-evaluate exits 12 and names the missing package.

tea-evaluate reads no BMAD configuration. Every subcommand takes --evaluation <path>, naming the evaluation folder or its evaluation.json, and exits 64 when that flag is missing or resolves to no evaluation.json. Nothing defaults to the working directory.

Platform checklist

Section titled “Platform checklist”

preflight and run confine every target before it starts, and stop with exit 12, naming what is missing, on a host that cannot confine or audit it. Check the host before the first live command:

  • macOS: /usr/bin/sandbox-exec (Seatbelt, part of macOS) and a session that may read the unified log through /usr/bin/log stream, which the audit reads. Start tea-evaluate from an unsandboxed terminal: sandbox-exec cannot apply a profile inside another Seatbelt sandbox, so a tea-evaluate started from a sandboxed shell (an agent’s tool, say) is refused. A subscription login kept in the Keychain has no grant under confinement; export CLAUDE_CODE_OAUTH_TOKEN from claude setup-token instead.
  • Linux: Bubblewrap’s bwrap on PATH (apt-get install bubblewrap), a kernel that allows unprivileged user namespaces and a network namespace, and strace 6.1 or later on PATH (apt-get install strace) with ptrace allowed, which the audit reads. A target that calls a model provider or another outside service lists its host in its registry entry’s egress, since a confined Linux target has a loopback and nothing else.
  • Windows: no confinement mechanism exists, so a confined preflight or run exits 12.

check, digest, status, score and compare launch no target and need none of these. ci needs them for the checks that run preflight or run (preflight-live and the live tiers); the checks of its pr tier launch no confined target. File-system confinement gives the full requirements, including the observer versions and the paths a host may not hold.

The evaluation folder

Section titled “The evaluation folder”

The runtime’s schemas ship under cli/lib/evaluate/schemas/ in the TEA package. They cover the manifest, probes, mutations, degenerate responses, held-out plan, evaluator files, judgment rows, framework versions, and evaluator qualification reports. contract.json and policy/scoring-policy.json meet the schemas eval-quality publishes. tea-evaluate Manifest describes each evaluation.json field and how the runtime reads it, and tea-evaluate Evaluators describes evaluator/ and policy/judge-calibration.json.

A baseline/qualification/ reference must resolve to a regular file inside the folder. The compare command runs the baseline-digest rule too, before it reads a baseline’s evidence (see Comparing).

digest

Section titled “digest”

digest writes corpus-index.json: every file under corpus/, probes/ and mutations/ as a path relative to the folder and the SHA-256 of its bytes, sorted by path. It prints the corpus digest, which is eval-quality’s artifact digest over that index, so any byte change in the corpus, the probes or the mutations moves it. Run it after every change to those folders; check refuses a stale index.

OptionMeaning
--evaluation <path>The evaluation folder, or its evaluation.json. Required.
--calibration-inputsPrint the values a records harness copies into its calibration judgments, and write nothing.
--file <path>Print the digest of one file the folder holds, named relative to the folder, and write nothing.

--file and --calibration-inputs cannot be combined.

Exit codes:

  • 0: the index was written, or the requested value was printed.
  • 10: an entry under corpus/, probes/ or mutations/ cannot be indexed, or --calibration-inputs met an evaluator that is not records, a contract with no rubric, an unusable labelled file or an unusable configuration.
  • 12: eval-quality is not installed.
  • 64: --evaluation is missing or resolves to no evaluation.json, --file names a path the folder cannot give (an absolute path, a .. segment, a symbolic link, a directory or a file the folder does not hold), or --file is combined with --calibration-inputs.

Output of the default form, which prints the corpus digest on its second line:

Output of --file requirements.md:

With --calibration-inputs, digest is read-only and prints the values a records harness copies into its calibration judgments (see The evaluation layer): it writes nothing under the folder, corpus-index.json included, and prints no corpus digest. The document on stdout holds calibrationDigest (eval-quality’s digestBytes over policy/judge-calibration.json, the value for tea.judgeCalibrationDigest), scorerConfigurationDigest (over <records>/evaluator-configuration.json without its two tea.judgeCalibration* bindings, so the file can exist without them) and items, one { "rubricId", "criterionId", "scorerInput" } per labelled item in the labelled file’s order. It carries no answer (your scorer supplies it) and no expectedLevel. check and run derive the same values with the same functions, so a change to how the runtime derives the observation or the digest changes this output and their verification together. It reads only what it needs and does not run check, so run check once the judgments file is written. It exits 10 with a judge-calibration finding for an evaluator that is not records, a contract that declares no rubric, a labelled file check refuses, or a configuration that is absent, a link, not JSON or off eval-quality’s evaluator-configuration schema.

With --file <path>, digest is read-only and prints eval-quality’s digestBytes over the bytes of one file the folder holds, as sha256: and 64 hex digits on one line. This is the value for requirements.digest in evaluation.json and for the contract’s sourceSpecDigest: both are the digest of the exact bytes of requirements.md, with nothing trimmed or normalized. It writes nothing under the folder, corpus-index.json included, and prints no corpus digest. The path is relative to the evaluation folder. It exits 64 with one line on stderr for an absolute path, a path with a .. segment, a symbolic link at any component, a directory, a file the folder does not hold, a path that cannot be read, an entry that is not a regular file or a file that changed while it was read, and for --file together with --calibration-inputs. Change one byte of the file and the printed digest changes.

Synopsis, with optional arguments in brackets:

Examples, for an evaluation with no partitionPlan and for the development partition of one that declares it:

OptionMeaning
--evaluation <path>The evaluation folder, or its evaluation.json. Required.

  • 0: the preflight passed.
  • 3, 4, 5: the exit of eval-quality preflight, passed through verbatim: 3 is a failed preflight, 4 a contract defect and 5 a runtime fault.
  • 64: an eval-quality stage’s own exit 64, passed through.
  • 10: an authoring defect: a check finding, a leg the registry does not authorize, or a mutation whose find text does not occur exactly once.
  • 11: an evaluation weakness: a seeded probe whose clean arm does not pass or whose mutated arm does not fail, a historical probe that does not fail before its fix or pass after it, or a gameability probe whose degenerate response the naive oracle rejects or the disciplined oracle accepts.
  • 12: infrastructure: a workspace that cannot be made, a target that cannot launch, a restore that fails, a change to your project during the run, or an engine stage that cannot run.
  • 64: --evaluation is missing, --partition names an unknown partition, or --partition is missing over a partitionPlan.

Output of a passing preflight over the one-skill evaluation in The evaluation.json fields (the invocation ID differs on every run):

With --partition, only that partition’s seeded probes are qualified, over the contract that partition runs (see Held-out probes and partition plans); an unknown partition exits 64 and a held-out set with no probe exits 10. When evaluation.json declares a partitionPlan, --partition is required: a preflight with no --partition exits 64 and names the flag and both values, because it would derive the both view and launch the held-out request. Preflight development while you author, and held-out after the development review. An evaluation with no partitionPlan preflights with no flag and qualifies every probe.

preflight checks the harness against the real target before trials begin. Each invocation writes runs/<invocationId>/ and creates runs/.gitignore on the first run. The steps run in order, each stopping the run with its own exit:

  1. check over the folder; any finding exits 10 and is printed as check prints it.
  2. The evaluation must be one this release runs: every seeded probe on the controlled-mutation or historical route (exit 12 otherwise, and a retry cannot pass); and when the registry declares an HTTP target, the evaluation’s HTTP port, started once and asked which protocol it speaks, must answer as TEA’s host (exit 10 otherwise, and 12 when its process cannot start or answer in time; see The HTTP port).
  3. The pristine workspace (see The workspace), with every registry target present and executable in it (exit 12 otherwise), and run.json.
  4. eval-quality compile and eval-quality seal over the run’s own copy of contract.json, writing eval-contract.json and sealed-evaluator-brief.json; a non-zero exit the CLI documents is passed through.
  5. Each seeded probe qualified through its controlled mutation (see Controlled mutations) or across its fix boundary, a fix commit or a pair of deployments (see Historical probes), exiting 10, 11 or 12 when a step fails; a historical probe with no revisions to address, naming a deployment the registry does not authorize, or naming one that reports another release than the one it declares or whose report request is denied or answered with no string at the pointer, is refused and left out. Each gameability probe qualified over its degenerate response with no target launched (see Gameability probes), exiting 11 when the naive oracle rejects it or the disciplined oracle accepts it; run reuses the result.
  6. The legs: eval-quality’s runPreflight plans them from the contract and the qualified probes (every sensitivity-witness leg, the minted control legs, and each defect’s manifestation-witness leg) and drives them through the adapter the registry authorizes, eval-quality’s command-line adapter for a command, its MCP adapter for a tool call, and the evaluation’s own HTTP port for an HTTP request. A manifestation witness’s leg runs in its mutation’s mutated workspace, or on the historical route in a worktree at the pre-fix revision or against the pre-fix deployment, and every other leg in the pristine workspace, each through an authorization whose working directory is that workspace. Each command request carries the host’s values for the environment keys its registry entry permits, each tool server and each started HTTP service starts with the host’s values for its entry’s keys, and each HTTP request carries its entry’s auth header. Every observation is written to observations/ as it arrives, with the request, the workspace and the working directory beside it; a request’s environment is recorded as its keys only, and every injected or server environment value and every auth value of eight characters or more is replaced by [redacted] in the observation’s strings, object keys and numbers, as written and in the JSON-escaped forms the registry lists, in whatever letter case the target echoes it (lower, upper, capitalized or mixed; a case mapping that changes a text’s length, such as ß to SS, and the Turkish i and I, included). A leg the registry does not authorize is refused by the adapter before it starts: the fault is written to faults/ and the command exits 10. A leg that cannot run at all (a budget exceeded, a process that fails to start) is written there too and exits 12, as does any other failure that stops the legs. A leg that exits one of its entry’s infrastructureExitCodes is an observation like any other: the CLI’s verdict reads it (a control leg that exits non-zero fails clean-control, exit 3), which ci classes as an infrastructure or integrity exit. A qualification arm step that exits one stops the cycle with exit 12, since an arm has no verdict to classify it. Once the legs have run, the pre-fix deployment of each historical arm is asked again which release each of its HTTP interfaces runs (see Against deployments). A release that changed refuses every probe on that pre-fix release: the probes leave probes.json and the observations the CLI reads, and the arm leaves run.json’s deployments. A deployment that cannot answer stops the run with exit 12, naming the point.
  7. eval-quality preflight --contract contract.json --probes probes.json --observations observations.json --run-id <invocationId> over the files in the run directory, probes.json holding the qualified probes that remain. Its preflight-verdict.json is the verdict, and its exit code is the command’s exit code, verbatim: 0 when the preflight passed, 3 when it failed.
  8. A passed verdict is then held to the mount allowlist score applies to a trial set’s isolation manifest. Each leg of the pristine workspace runs under the same audit as a trial (see File-system confinement). A path that every one of those legs opened outside what it was granted exits 3, the exit score gives a trial that opens it: a target that lives outside its workspace loads its own files on every launch, so every trial opens them too. The message names the first paths and the two setups that work for such a target, tea-skill-runner named by its bare name for one: a registry target that is a path inside launch.root (node_modules/.bin/tea-skill-runner over a copy workspace, or over a git workspace with workspace.provision), or the bare name with the directories it runs from listed in systemPaths, the bin directory that holds its link on PATH among them. A path that only some legs opened is no refusal: preflight prints a note naming the path and the legs that opened it, and its exit does not change, since score judges the trials and not the legs. Only the legs whose audit lost no report take part in that check, because a path a lossy audit dropped is no evidence that the leg did not open it. A leg whose audit lost events, delivered fewer of its canary reads than it sent, or ran while reports reached the log faster than it keeps them, is left out, and preflight prints a note naming it; no note says the other legs did not open a path on its word. When every leg’s audit lost reports, no leg can say what it opened, so preflight exits 12 with the legs yield no audit and the advice to run again on a quieter host, in place of passing. The check grants nothing and widens no allowlist; a run that opted out of confinement observes no path and is not refused.

runPreflight computes a verdict of its own, and preflight discards it: every verdict comes from the CLI over files you can rerun by hand from the run directory. engine/<stage>.json records each stage’s executable, argv, exit code, stdout and stderr, with the path forms of Paths in the records. A stage that cannot start, is killed by a signal, or exits with a code eval-quality does not document for that stage exits 12. A SIGINT, SIGTERM, SIGHUP or SIGQUIT that reaches check, preflight, run, score or ci while a stage runs stops the stage’s process group first, then the command removes its private directories and ends by the same signal. The documented codes: compile and seal 0, 4, 5 and 64; preflight 0, 3, 4, 5 and 64; score 0, 2, 3, 4, 5 and 64; aggregate-strength 0, 4, 5 and 64. Setting ENGINE_CLI_ENV substitutes another executable for the eval-quality CLI; tea-evaluate announces the substitution on stderr and records it in each stage’s record.

File-system confinement

Section titled “File-system confinement”

run and preflight confine every target they start. Confinement limits what a target can do on your host, and the two platforms limit reads differently:

  • On both platforms a confined target writes only its workspace and the private directories the runtime hands it, cannot read or write the evaluation folder (the contract, the probes and which defect a mutation plants), cannot read or write your git directory and cannot reach the evaluation layer’s private files.
  • macOS blocks reads: Seatbelt refuses file data outside the target’s grants with EPERM before the read happens. A macOS target keeps the host’s network.
  • Linux detects reads afterwards: Bubblewrap gives the target a read-only view of /, so a file outside its grants that Bubblewrap does not hide can be read. strace records each such read, and run and score refuse the trial that made it (exit 3, mount outside allowlist), after the read happened. Keep files a target must not read off a Linux evaluation host, or run in a container that does not hold them. The network is closed apart from a loopback and the hosts egress lists.

"confinement": false removes these limits

Setting "confinement": false in evaluation.json runs every target with your user’s file system, network, home directory and credentials, with no audit. A target can read any file you can read and write outside its workspace; the run notices a change to your project or its git state afterwards and exits 12, and a write anywhere else goes unnoticed. No read outside the workspace is observed, so score cannot refuse a trial for one. run.json records "confinement": "opt-out" and score says so in its summary line. Opt out only for a target that cannot run confined (one that must commit, read the project’s git directory or open a network route that is no HTTPS CONNECT tunnel), and state the reason in the change that sets the field.

tea-evaluate Confinement describes what a confined process can read, write and reach, the audit, egress and subscription logins in full.

Record a before state

Section titled “Record a before state”

A skill with known defects fails its clean controls, and run stops with exit 11 on the first one. --before-state records that starting point, so a later evaluation of the fixed skill has something to compare with.

A clean control declares its known defect in its attestation: a qualification.noKnownDefectStatement that begins Known defect at this revision: and says what fails. The statement for a control that passes stays No known defect at this revision.

Under the flag, a control that declares a known defect may fail its baseline when its oracles are violated; its evidence goes to qualification/<probeId>/baseline-known-failing.json. Every other control must still pass, and a control with an oracle that cannot decide still exits 11. The flag covers clean controls only: the clean arm of a seeded probe must still pass its preflight qualification, so a defect that also breaks a seeded probe’s baseline still exits 11 there. A control that declares a known defect and passes is recorded too, and the closing line names it, because its statement is stale. The flag exits 64 when no selected control declares a known defect.

run.json gains beforeState, which lists each declaring control with its statement and the disposition its baseline had (violated or held). The closing line of run and of score repeats it, in capitals, as BEFORE STATE. score runs as usual and eval-quality computes every state: a known-failing control whose trials violate its oracles scores false-positive, so score exits 2 and the evidence artifacts hold the before state. TEA records the declaration and computes no verdict.

A before state is excluded from baseline acceptance. compare and compare --accept exit 10 on a run that records beforeState, and on any run whose sealed clean control still declares a known defect, so deleting the record by hand changes nothing. Once the defect is fixed, change the control’s statement to No known defect at this revision., run without the flag and accept that run.

Accepting a baseline

Section titled “Accepting a baseline”

compare --accept replaces baseline/ wholesale with a byte-identical snapshot of the run. A baseline changes only through this command, in a reviewed pull request; commit it with the change that moves the engine, the contract, the corpus or the policy. Commit baseline/ before the next run, since an uncommitted baseline inside a repository makes that run record dirty: true.

compare --accept is the only command that writes. Before it looks at the run, it takes an exclusive lock with one mkdir of runs/.compare-staging.lock (a pid file inside names the holder for the message) and keeps it through the swap and cleanup. A lock directory that already exists makes the accept exit 12 naming runs/.compare-staging.lock and the pid when it can be read; nothing decides a lock is stale or takes one over, so when no accept is running (an earlier accept was killed with SIGKILL), delete that directory by hand and run the accept again. A Ctrl-C or SIGTERM removes the lock and exits with the shell’s signal status (128 plus the signal number); the staging leftover stays for the next accept’s recovery. A runs/ that is a link or a file, or a lock path that cannot be created, exits 12 with the real error text. Under the lock it puts a retired baseline back when baseline/ is absent (see below) and deletes stale staging and retired directories.

The refusal order is fixed:

  1. No run, a run that did not complete, or a run with no score invocation: exit 64.
  2. dirty: true in run.json: exit 10 with nothing written. A run measured over uncommitted work (--from-working-tree over a change) is never accepted, and there is no flag that overrides it. A before state (run --before-state, or a run whose sealed clean control declares a known defect) is refused the same way, by compare as well as compare --accept.
  3. One pass over the run that reports every finding it makes: a probe with no evidence artifact in the latest score invocation, a member the replay needs that is missing, a link (a directory above a member included), any entry that is not a regular file, an actions artifact whose bytes differ from the digest its record names, and a latest scores/<scoreInvocationId>/score.json that does not parse, does not name this run and invocation, records an exit other than 0, 2 or 3 (12, 64, 4 or 5) or records a strength aggregate that was refused, failed or disagreed with the evidence score persisted. Exit 10 naming each, with nothing written; a score.json finding says to score the run again. A weak result stays acceptable: a probe the corpus did not catch exits 2.
  4. Only when step 3 found nothing: every finding the input checks score runs over the run’s artifacts would report (an edited sealed record or operation phase snapshot, for example), so no run score would refuse becomes a baseline. Exit 10 with nothing written.
  5. The copy. The snapshot is staged under runs/.compare-staging/ (gitignored, on the same file system as baseline/, so each rename is atomic), each staged file is read back and held to the digest of the bytes it was staged from, and the directory is swapped in as the last step. A failure while staging or swapping removes the staging directory, restores the previous baseline/ and exits 12, so a refused or failed accept leaves the old baseline byte-identical; when restoring it fails too, the message says baseline/ is absent and where the previous baseline lies.

Nothing is staged inside the committed evaluation folder, so an accept that is interrupted leaves no untracked entry there for the next run to record as dirty: true. An accept interrupted between its two renames leaves baseline/ absent and the previous baseline under runs/.compare-staging/retired-*. The next compare --accept puts it back under its lock (a restore that fails reports the real state, where the retired baseline lies, and exits 12) and deletes stale staging and retired directories. A plain compare is strictly read-only and never restores or deletes: with baseline/ absent and a retired copy present it exits 10 naming the copy (and the lock, when one is present), since an accept either stopped there or is still running.

baseline/ mirrors the run directory’s relative paths, byte for byte, so every digest run.json recorded still matches. The sealed records name their actions artifacts and isolation manifests as runs/<acceptedRun>/... paths, and score refuses a reference outside the run directory it scores, so a replay places the baseline’s bytes at runs/<acceptedRun>/ inside a scratch copy of the evaluation folder; under any other id, or under runs/<id>/replay/, the records would reach outside their run. No file is rewritten, since the runtime recorded the neutral forms in the first place and every digest was taken over those bytes. It holds:

ci

Section titled “ci”

ci runs exactly the checks ci/evaluation-ci-plan.json places on one tier, pr, merge, scheduled or release: the plan is the only definition of tier membership. The live tiers

Section titled “The live tiers”

preflight-live runs preflight over every partition and exits as it does; CI is no authoring step, so a partitionPlan does not require it to name one. The strength floor is read from the floor decisions eval-quality records in the strength aggregate of the twin run and of the held-out run, each on its own. A class that does not meet its floor warns on scheduled and exits 2 on release.

Declare a floor only for a class that the partition it is read on can hold an eligible probe of. A probe is eligible for the strength vector when it is not a canary and not expectedClean, so a clean control, which is also the zero-action class, never fills a floor: a zero-action floor reads no-eligible-probe and does not meet it unless each partition it is read on holds a zero-action defect probe, which a behavior that must take an action (its missing action is the defect) needs. An evaluation whose behaviors all respond to a request declares defect and, once it holds a gameability probe in each partition, gameability, and no zero-action floor. The twin run repeats the partition baseline/ recorded and the held-out partition is read on its own, so every class whose floor the evaluation declares needs an eligible probe in the partition baseline/ records (the corpus without heldOutProbes for a development baseline, the whole corpus for a both baseline) and one in heldOutProbes: a gameability or zero-action floor needs two probes of that class for a development baseline, one held out and one in the recorded partition, beside the defect probes. The Evaluate skill’s starter evaluation.json declares the defect floor alone for that reason.

Exits and the evidence

Section titled “Exits and the evidence”

A check that needs an absent baseline/ exits 64; accept a scored run with compare --accept before rerunning it. api-conformance also exits 64 when evaluation.json names no HTTP entry in its registry.

The final exit is the most severe blocking result, in this order: 64, 12, 5, 4, 3, 13, 11, 10, 2, 1, then 0. Each exit has a class and an action: eval-quality’s 2 (target behavior failure), 3 (infrastructure or integrity), 4 (contract authoring defect), 5 (runtime fault) and 64, tea-evaluate’s 10, 11, 12, 13 and 64, and a gate’s 1 (repository policy violation) and 64, each blocking. A gate exit outside that table passes through as an undocumented exit, blocking, ranked after 1. A gate check runs as a child process in a process group of its own, with the plan’s argv, no shell and stdin closed. It ends at its plan check’s timeoutMs (600000 when absent): the group gets SIGTERM, then SIGKILL after two seconds, and the check exits 12. It ends the same way, with the bytes up to the bound kept, when it prints more than 64 MiB; exactly 64 MiB passes. Whatever the gate left running in its process group, a descendant that holds no stream included, is killed when the gate exits. What the gate printed is persisted whatever the exit. A SIGINT or SIGTERM to ci ends whatever the running check is waiting on at once: a gate, or an eval-quality stage (the plan’s compile and seal, the replay’s preflight, score and aggregate-strength, the stale-baseline compile, the compile check runs, and the stages of a live check). The group of the gate or stage gets the signal and is killed half a second later, ci removes its scratch directory, and then ci ends by the same signal. Only a SIGKILL of ci itself leaves a running gate or stage in its own process group, since no portable parent-death signal exists; the next ci over the folder removes the scratch directory it left, the one a check check made included.

runs/<invocationId>/ holds ci.json (the tier, each check’s id, exit, class, action, enforcement, evidence paths, warnings and notes, and the final exit), and per check checks/<id>/exit-code, stdout and stderr as the check printed them, whatever the exit (an evaluate check in the path forms of Paths in the records, a gate as your command printed it); the engine’s call records and outputs of compile, seal and the replay (replay/preflight-verdict.json, replay/scores/, replay/engine/preflight.json) sit beside them, and a live check’s own run directories stay under runs/.

How the skill runner supervises its agent

Section titled “How the skill runner supervises its agent”

tea-skill-runner runs one headless agent turn and has to report how it ended, whatever the agent does. It cannot trust the agent to end its own children, to answer a signal or to stay in one process. A registry entry’s maxElapsedMs must leave room for the startup and shutdown reserves below.

On POSIX, the agent runs in its own process group. When the agent exits, every process left in that group receives SIGKILL at once. The group is also stopped when --timeout-ms runs out, when the runner’s process group receives SIGINT, SIGTERM, SIGHUP or SIGQUIT (a terminal’s Ctrl-C or Ctrl-\ included), and when the runner or the supervisor process between it and the agent dies, by SIGKILL included. Stopping sends the group the signal received (SIGTERM for a timeout or a death), and the group SIGKILL 2 s later if it is still running. An agent the SIGKILL ends is reported as killed by SIGKILL once it outlived the grace period after the signal that asked it to stop; a SIGQUIT can end that way wherever the system hands core files to a collector, since writing the core can take longer than the grace period. A Ctrl-Z suspends the runner, and the agent runs on, bounded by --timeout-ms and the runner’s end. Once resumed, the runner reports how the agent ended, however long it was suspended. On POSIX, four processes supervise the agent: one in the runner’s process group, a leader in a session of its own, a guardian that leads the agent’s process group, and a detached watchdog. The guardian’s lifeline closes even if the supervisor and leader receive SIGKILL together; it then stops its group. While the runner remains active, a missing-report transport failure is bounded by a 25 s startup reserve, the agent’s --timeout-ms wall clock, and 7 s for supervisor backstop and output drain. On POSIX, a detached watchdog owns the guardian’s group through a leader-only pipe. It confirms readiness before the guardian starts the agent. If the leader dies, the pipe closes and the watchdog sends SIGKILL to the group, even while the guardian is stopped. After a normal agent exit, the leader kills the group and releases the watchdog. The process integration gate requires the guardian, agent, and ordinary child to end within 10 s of a simultaneous leader and supervisor kill. The guardian allows 10 s for watchdog setup, and the agent’s --timeout-ms wall clock starts when its PID is reported. If the watchdog cannot arm, the agent does not start and the runner reports a setup failure. The agent’s standard input, output and error are pipes the group leader owns, and the leader copies the runner’s input to the agent and the agent’s output to the runner. Once the agent exits, the leader copies what those pipes still hold and closes each one when it reaches its end, stays empty for 100 ms, or has been read for 2 s of the time the runner keeps up with it; output any process writes after that is lost. A process that leaves the group, such as a daemon that starts its own session, keeps running, and the runner does not wait for it. If the group leader has not ended 5 s after --timeout-ms runs out (it was stopped with SIGSTOP, say), the other kills it and the agent’s group, and the runner exits 4. On Windows, a PowerShell helper creates a Windows Job Object with kill-on-close ownership and assigns the guardian before the agent starts. The guardian launches the helper from the host’s absolute SystemRoot path, so a project-local powershell.exe cannot claim readiness. The agent and its ordinary descendants inherit that job. The helper holds its sole job handle until the guardian closes their pipe after the agent exits, or the pipe closes when the guardian dies. Closing the handle stops every process in the job. The guardian allows 90 s for setup. The supervisor has a 105 s startup backstop measured from its own start, covering cold Node startup before the guardian’s timer begins. If the helper cannot establish ownership, the agent does not start and the runner exits 4 with the setup failure. The leader reports its guardian PID, agent readiness, and completion to the supervisor over a dedicated pipe with a 2 s write bound; a failed report stops the guardian. The --timeout-ms wall clock starts when the guardian reports the actual agent PID; the supervisor’s 5 s agent backstop follows that clock. The Windows process integration gate requires the direct agent and its child to end within 10 s of normal agent exit or a dual leader and supervisor kill.

Where the runner lives

Section titled “Where the runner lives”

On macOS an undeclared runner outside the read grants cannot load its source. preflight names captured denials and the setup below even when its verdict fails. run can stop at its verdict before any trial is sealed. score then exits 64 because that incomplete run has no trials to score.

A confined trial reads its workspace, the system’s own paths and the paths its registry entry lists in systemPaths. The runner is a program the trial starts, so the audit lists each of its files that lies outside those places. On macOS, the kernel refuses an undeclared source load, and preflight reports the attempted paths with exit 3. Exit codes

Section titled “Exit codes”

Exit 0 does not always mean the target passed

  • score exits 0 for PASS, WAIVED and CONCERNS alike, and its summary names only the exit; each probe’s evidence artifact under scores/ says which, in contractVerdict, or in productionVerdict for the production-mode records a records evaluator imports.
  • compare exits 0 for every comparison outcome: compared (whatever the relation, a run weaker than the baseline included), first-run and refused. Read its lines for the outcome.
  • compare --accept exits 0 and records the run as the baseline even when score exited 2 (FAIL), and after an exit 3 (Invalid) whenever every probe still has its evidence artifact. Accepting records a reference point for later comparisons; it certifies nothing about quality, so review the scored evidence before you accept.
  • Exits 2 to 5 carry eval-quality’s verdicts and faults, apart from ci’s 2 for a breached strength floor on release; ci adds 1 for a gate’s policy violation, and 10, 11, 12, 13 and 64 are TEA’s own validation, weakness, infrastructure, drift and usage exits. Exit codes lists them all.
  • ci is where enforcement lives: the CI plan places each check on a tier, and one fixed table of exits and actions decides what blocks, what warns and what passes. Exits and the evidence gives that table’s order, and Put an Evaluation in CI wires it into a pipeline.

Each command section above lists its causes and options. For ci, the final exit is the most severe blocking result in the order given by Exits and the evidence.
